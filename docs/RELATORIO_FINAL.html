1. Resumo da entrega

O projeto implementa um serviço de encurtamento de URLs em C++17. A aplicação expõe endpoints HTTP para criar links, redirecionar e consultar métricas. Os registros e eventos de clique podem ser persistidos em arquivos JSON Lines, e os principais componentes têm testes unitários e de integração.

Escopo funcional

  • POST /shorten: cria código curto para URL válida e aceita expiração opcional.
  • GET /{short_code}: redireciona com HTTP 302; códigos inexistentes ou expirados retornam 404.
  • GET /{short_code}/stats: apresenta destino, cliques e timestamps associados.
  • Geração base62, validação de URL e código, resolução de colisões e persistência local.

2. Arquitetura e decisões

A API HTTP, implementada com cpp-httplib, delega a lógica de negócio a RedirectService. Esse serviço coordena a geração de códigos, o armazenamento de URLs e o rastreamento de cliques. UrlStore e ClickTracker têm implementações adequadas a testes em memória e persistência JSON Lines para execução local.

API HTTP. Rotas, validação dos payloads e respostas HTTP/JSON; testes exercitam criação, redirect, stats e entradas inválidas.
RedirectService. Orquestra criação, expiração, destino e contabilização; links expirados não recebem novos cliques.
CodeGenerator. Gera códigos base62 e consulta colisões; std::hash não garante códigos estáveis entre toolchains.
UrlStore / ClickTracker. Armazenam links e histórico de cliques; arquivos locais são sincronizados dentro de um processo, e compartilhar entre processos não é suportado.

ADRs consolidados

  1. Geração de códigos: hash truncado com salt de tentativa e resolução de colisão pelo storage; sem promessa de estabilidade entre implementações de std::hash.
  2. Persistência: append-only em JSON Lines para simplicidade e recuperação após reinício; linha inválida causa erro explícito, não descarte silencioso.
  3. Dependências: cpp-httplib, nlohmann/json e GoogleTest obtidos por CMake FetchContent em versões fixadas.
  4. Expiração: link expira quando now >= expires_at; analytics permanece disponível, mas redirect expirado retorna 404 sem incrementar cliques.

5. Retrospectiva do autor

Relato fornecido pelo autor sobre o ciclo de desenvolvimento: a dificuldade principal foi manter build e testes consistentes entre máquinas com/sem Docker e entre CMD/PowerShell, além de uma credencial Git de outra pessoa salva no Windows. Entre os problemas mencionados estão um code_generator.cpp antigo copiado por engano (237 bytes em vez de 1537), omissão de url_store.cpp no CMakeLists.txt e push 403 porque outra conta estava autenticada.

Segundo o relato, as respostas adotadas durante o ciclo foram tratar GitHub Actions como fonte de verdade para builds limpos no Ubuntu com ASan, UBSan e ThreadSanitizer; criar arquivos por comando e conferir tamanho/conteúdo antes de commits; trabalhar em clones limpos; configurar identidade Git apenas no repositório; e remover a credencial do Windows ao terminar. O aprendizado apontado pelo autor é exigir evidência objetiva (tamanho do arquivo, log do CI ou captura) e versionar a configuração do ambiente, em vez de depender da memória.

Esta seção é retrospectiva fornecida pelo autor sobre o ciclo; não afirma que todas as medidas foram executadas nesta sessão. O workflow atual comprovado neste relatório usa ASan e UBSan; ThreadSanitizer não foi alegado como resultado atual.

7. Análise ético-técnica

A. Alucinação e confiabilidade

Assistentes podem sugerir código ou explicações incorretos, inclusive em concorrência, datas e validação. Testes, contratos explícitos, sanitizers ASan/UBSan na CI e coverage são controles observáveis, mas não substituem compreensão e verificação do autor nem comprovam ausência de falhas.

B. Privacidade e dados

URLs e timestamps de cliques podem conter ou revelar dados pessoais. O serviço os persiste localmente em JSON Lines. Recomenda-se usar dados sintéticos em demonstrações, restringir acesso ao diretório e evitar publicar registros.
